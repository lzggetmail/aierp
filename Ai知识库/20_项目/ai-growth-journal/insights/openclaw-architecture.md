## 核心架构

```
┌─────────────────────────────────────────────┐
│           Gateway（总控制中心）               │
│         一个进程，管理所有龙虾                │
└─────────────────┬───────────────────────────┘
                  │
        ┌────────┴────────┐
        │    绑定规则      │
        │  （路由分配）    │
        └────────┬────────┘
                 │
    ┌────────────┼────────────┐
    │            │            │
┌───▼───┐   ┌───▼───┐   ┌───▼───┐
│大龙虾  │   │小龙虾  │   │蓝龙虾  │
│(main) │   │(work) │   │(family)│
│       │   │       │   │       │
│独立工作区│   │独立工作区│   │独立工作区│
│独立记忆  │   │独立记忆  │   │独立记忆  │
│独立会话  │   │独立会话  │   │独立会话  │
└───────┘   └───────┘   └───────┘
```

## 关键理解

### 1. 为什么可以"养多只龙虾"？

**核心原理**: 一个 Gateway + 多个 Agent

每只龙虾（Agent）有独立的：
- **Workspace**: 工作区（文件、配置）
- **agentDir**: 状态目录（认证）
- **Sessions**: 会话存储（聊天历史）
- **Auth**: 认证信息（不共享）

### 2. 绑定规则是什么？

**本质**: 路由规则，决定谁的消息给哪只龙虾

**优先级**:
1. peer（具体群/人）— 最精确
2. accountId — 账号级别
3. channel — 渠道级别
4. 默认 agent — 兜底

### 3. 这有什么用？

| 场景 | 应用 |
|------|------|
| 多人共用一台服务器 | 每个人有自己的龙虾，记忆不串台 |
| 不同渠道用不同龙虾 | 飞书用便宜的，Telegram用强大的 |
| 一个群专用一只龙虾 | 家庭群用家庭龙虾，工作群用工作龙虾 |

---

## 我的思考

这个架构的设计很聪明：
1. **隔离** — 每只龙虾独立，不会互相干扰
2. **灵活** — 可以根据需要配置不同的龙虾
3. **经济** — 不同龙虾可以用不同模型（便宜的干轻活）
4. **安全** — 可以限制某些龙虾的权限
