## 一、整体架构

```
┌─────────────────────────────────────────────────────────┐
│                    用户层                                │
├─────────────────────────────────────────────────────────┤
│  老客户：Delphi 客户端（核心业务，继续维护）              │
│  新客户：Web 端 + 飞书端（双端配合使用）                  │
└─────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────┐
│                    双端职责划分                          │
├──────────────────┬──────────────────────────────────────┤
│    Web 端         │            飞书端                    │
├──────────────────┼──────────────────────────────────────┤
│ 规范性数据录入    │ AI Chat 交互入口                     │
│ 核心业务操作      │ 汇总类数据展示                       │
│ 复杂表单处理      │ 任务类数据管理                       │
│ 报表查询与导出    │ 7×24 监控预警                       │
│ 系统配置管理      │ 移动端便捷操作                       │
└──────────────────┴──────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────┐
│                    AI 层（QClaw/QwClaw）                 │
├─────────────────────────────────────────────────────────┤
│  AI Agent + Skills（数据分析、问题发现、建议生成）       │
└─────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────┐
│                    数据层                                │
├─────────────────────────────────────────────────────────┤
│  后端：SQL Server（核心业务数据）                        │
│  前端：飞书多维表格（汇总数据、任务数据）                 │
└─────────────────────────────────────────────────────────┘
```

## 二、核心设计理念

### 2.1 双端架构

| 端 | 职责 | 说明 |
|------|------|------|
| **Web 端** | 规范性、核心业务 | 严格约束、复杂操作、PC 端为主 |
| **飞书端** | 便捷性、协作、AI 交互 | 灵活便捷、移动端友好、AI Chat |

### 2.2 数据分层

| 层 | 数据类型 | 数据量级 | 原因 |
|------|---------|---------|------|
| **后端 SQL Server** | 核心业务数据 | 50 张表，百万级 | 强一致性、高并发、事务支持 |
| **前端飞书多维表格** | 汇总协作数据 | 20 张表，千级 | 灵活扩展、多视图、协作编辑 |

### 2.3 AI 层定位

**AI = 顾问，不是工具**

| AI 助手 | AI 顾问 |
|---------|---------|
| 帮员工干活 | 帮老板发现问题 |
| 提高效率 | 降低风险、优化决策 |
| 客户觉得"省点事" | 客户觉得"值钱" |

---

## 三、Web 端职责

| 场景 | 使用 Web 端的原因 |
|------|------------------|
| **订单录入** | 需要严格的字段约束、必填校验、数据格式化 |
| **库存管理** | 需要精确的数量控制、批次管理、仓库区分 |
| **财务记账** | 需要借贷平衡、科目校验、凭证规范性 |
| **基础数据维护** | 客户档案、产品档案、供应商档案需要规范化 |
| **复杂报表查询** | 多条件组合查询、数据导出、打印 |
| **系统配置** | 权限配置、流程配置、参数设置 |

**Web 端 = 规范性、核心业务**

---

## 四、飞书端职责

| 场景 | 使用飞书端的原因 |
|------|------------------|
| **AI Chat 查询** | "上个月销售情况怎么样？" —— 自然语言更便捷 |
| **汇总数据查看** | 老板看仪表盘、关键指标 —— 可视化展示 |
| **任务管理** | "张三今天要干什么" —— 任务看板、日历视图 |
| **进度跟踪** | 生产进度、订单进度 —— 多视图展示 |
| **考核分析** | 人员绩效、部门效率 —— 图表化呈现 |
| **移动端操作** | 外出时快速查询、审批 —— 手机方便 |
| **7×24 预警** | 异常自动推送 —— 实时通知 |

**飞书端 = 便捷性、协作、AI 交互**

## 五、数据分层设计

### 5.1 后端数据库：40-50 张表（核心业务）

| 表类型 | 表数量 | 数据量级 | 原因 |
|-------|--------|---------|------|
| 基础数据 | 10-20 张 | 5 万+ 条 | 需要严格约束、频繁查询 |
| 业务数据 | 20-30 张 | 50 万+ 条 | 核心交易、高并发、强一致性 |
| 系统数据 | 5-10 张 | 100 万+ 条 | 日志、审计、配置 |

### 5.2 前端数据库：10-20 张表（汇总 + 协作）

| 表类型 | 表数量 | 数据量级 | 原因 |
|-------|--------|---------|------|
| 汇总数据 | 5-10 张 | 几千条 | 聚合后的数据，数据量小 |
| 任务数据 | 3-5 张 | 几百条 | 协作数据，日常使用 |
| 分析结果 | 3-5 张 | 几十条 | AI 生成，数量有限 |

### 5.3 数据分类决策树

```
数据需要存到哪里？
    ↓
是核心业务数据吗？（订单、库存、财务、生产等）
    │ 是                        │ 否
    ↓                           ↓
后端数据库              是汇总/统计数据吗？
                        │ 是          │ 否
                        ↓             ↓
                    前端数据库    是任务/协作数据？
                                    │ 是      │ 否
                                    ↓         ↓
                                前端数据库  后端数据库
```

## 六、数据同步方案

### 6.1 同步策略

| 数据类型 | 同步方式 | 频率 | 原因 |
|---------|---------|------|------|
| **基础数据** | 定时同步 | 每小时 | 变更不频繁，延迟可接受 |
| **业务数据** | 实时同步 | 立即 | 需要及时反馈 |
| **汇总数据** | 定时聚合 | 每天 | 统计分析用，不需要实时 |
| **任务数据** | 双向同步 | 实时 | 协作需要，两边都可能改 |
| **分析结果** | 单向写入 | 按需 | AI 生成后直接写飞书 |

### 6.2 技术实现

| 技术栈 | 说明 |
|--------|------|
| **编程语言** | Node.js（推荐）/ Python（备选） |
| **飞书 SDK** | @larksuiteoapi/node-sdk / lark-oapi |
| **SQL Server 驱动** | mssql / tedious / pymssql |
| **部署** | Docker 容器化 + 定时任务 |

## 七、AI 层设计

### 7.1 核心能力

| 能力 | 说明 |
|------|------|
| **执行能力** | 给 AI 配一台电脑，通过聊天接收指令并完成任务 |
| **拥有记忆** | 能记住你的偏好，真正做到懂你、专属于你 |
| **持续进化** | 开源技能社区，让 AI 可以快速掌握各类技能 |
| **主动 7×24 小时干活** | 24 小时无休干活，定时执行，主动汇报、自主组建团队 |

### 7.2 技术选型

| 方案 | 优势 | 适用场景 |
|------|------|---------|
| **QClaw** | 国内大厂背书、安全保障 | 通用场景 |
| **QwClaw** | 企业级安全、合规性强 | 对安全要求高的客户 |
| **OpenClaw** | 开源、灵活 | 技术团队强、可自维护 |

## 八、核心公式

**AiERP = 老系统（不动） + Web 端（规范） + 飞书端（便捷） + AI 层（顾问） + 双数据源（分层）**

---

## 九、设计亮点

| 亮点 | 说明 |
|------|------|
| **不推翻老系统** | Delphi 客户端继续维护，老客户不受影响 |
| **双端各司其职** | Web 端管规范，飞书端管便捷 |
| **数据分层** | 核心数据在后端，汇总数据在前端 |
| **AI 层独立** | AI 不侵入核心业务，只做分析和建议 |
| **渐进式升级** | 先上 AI 特性，后优化底层 |

---

## 十、与传统 ERP 对比

| 传统 ERP | AiERP |
|----------|-------|
| 单一客户端 | 双端（Web + 飞书） |
| 单一数据源 | 双数据源（SQL Server + 飞书多维表格） |
| 无 AI | AI 顾问层 |
| 推倒重来 | 渐进式升级 |
| 工具 | 顾问 |
