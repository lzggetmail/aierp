# AiERP 产品规划讨论记录

> 日期：2026-03-18
> 项目：AI 驱动的轻量化企业诊断系统
> 参与者：产品团队

---

## 一、项目背景

### 1.1 现有基础
- 十多年深耕的 Delphi CS 架构 ERP 系统
- 垂直领域（制造业）业务逻辑成熟
- 客户定位：中小微企业（非大企业）

### 1.2 现实约束
- 技术力量薄弱
- 客户"不见兔子不撒鹰"（要看到结果才肯买单）
- 成本有限，无法像大厂一样重金投入
- 品牌影响力不足

### 1.3 核心矛盾
| 传统 ERP 思维 | 未来企业趋势 |
|--------------|-------------|
| 一套系统覆盖所有业务 | 小型化、轻量化需求 |
| 重流程、重约束 | 快速响应、灵活应变 |
| 大企业才用得起 | 一人公司、微型团队 |

## 二、核心策略：渐进式 AI 升级

### 2.1 不推倒重来
```
现有 Delphi ERP + 本地数据库
         ↓
Web 前端重构 + AI 层（先上马）
         ↓
非结构化数据库迁移（MongoDB 等）- 逐步优化
```

### 2.2 数据策略：放宽数据约束

| 传统做法 | 轻量化做法 |
|---------|-----------|
| 严格的数据库约束（非空、唯一、外键） | 放宽限制，允许数据不完美 |
| 十级审批流，层层上报 | 1-2 层审批，其余用 AI Chat 处理 |
| CS 架构桌面客户端 | Web 前端，随时随地访问 |

**核心逻辑**：
- 数据"脏一点没关系"，AI 可以处理、理解、补全
- 流程"简一点没关系"，AI 可以辅助判断、决策
- 系统"轻一点没关系"，中小客户要的是解决问题

### 2.3 开发原则：先上马，后优化
- 快速展示 AI 价值
- 客户看到效果再投入
- 逐步迭代底层架构

## 三、产品定位

### 3.1 核心价值主张

**不是 AI 助手，而是 AI 顾问**

| AI 助手 | AI 顾问 |
|---------|---------|
| 帮员工干活 | 帮老板发现问题 |
| 提高效率 | **降低风险、优化决策** |
| 替代简单劳动 | **替代昂贵顾问** |
| 客户觉得"省点事" | **客户觉得"值钱"** |

### 3.2 产品定位

> **AI 驱动的企业经营诊断系统**
>
> 不是 ERP，而是 **ERP + AI 顾问**
>
> 核心价值：**让每个中小企业都拥有"全职 CFO + 运营顾问"**

### 3.3 Slogan 思考
- "你的数据会说话，我们帮你听懂"
- "AI 顾问，24 小时帮你盯着的财务总监"
- "发现你看不到的问题"

## 四、参考案例：阿里悟空

### 4.1 悟空的核心思想

**从"对话式 AI"到"行动式 AI"**

| 传统对话式 AI | 悟空行动式 AI |
|--------------|--------------|
| "怎么查库存？" | **直接帮你查库存** |
| "怎么分析财务数据？" | **直接生成分析报告** |
| "怎么优化人力？" | **直接给出优化方案** |

### 4.2 "一人团队"愿景

```
传统企业结构：
老板 + 财务主管 + 生产主管 + 人事主管 + 采购主管 + ...
         ↓
AiERP 一人团队：
老板 + AI 财务顾问 + AI 生产顾问 + AI 人事顾问 + AI 采购顾问 + ...
```

### 4.3 技术架构参考

```
用户指令
    ↓
Agent（大模型）理解意图
    ↓
调用 Skill / Tool（执行具体操作）
    ↓
返回结果 + 自动生成汇报
```

## 五、核心功能场景

### 5.1 人力资源分析

| 问题 | AI 怎么发现 |
|-----|-----------|
| 岗位是否饱和？ | 分析工作量、产出、加班数据，对比行业基准 |
| 加人还是减人？ | 模拟不同产能下的人力需求，给出最优方案 |
| 谁在摸鱼？ | 异常检测：任务完成时间异常、工作量明显偏低 |
| 谁要离职？ | 行为模式分析：效率下降、请假增多、消极指标 |

### 5.2 财务健康诊断

| 问题 | AI 怎么发现 |
|-----|-----------|
| 利润为什么下降？ | 多维度分析：成本上涨？销量下滑？产品结构问题？ |
| 哪些产品在亏钱？ | 计算每个产品的真实毛利率，发现"隐形亏损品" |
| 现金流会不会断？ | 预测未来 3 个月现金流，提前预警风险 |
| 哪些客户有问题？ | 分析回款周期、退货率、投诉率，发现"毒客户" |

### 5.3 生产运营优化

| 问题 | AI 怎么发现 |
|-----|-----------|
| 生产瓶颈在哪里？ | 分析各工序等待时间、在制品积压，找到"卡点" |
| 库存是否合理？ | 对比库存周转率与行业水平，发现积压或短缺 |
| 为什么交货延期？ | 追溯延期订单的根因：原料？设备？人员？ |
| 质量问题在哪？ | 分析不良率与工艺、人员、批次的相关性 |

### 5.4 隐性问题发现

| 问题 | AI 怎么发现 |
|-----|-----------|
| 有没有人在舞弊？ | 异常交易检测：频繁退货、异常价格、关联交易 |
| 流程哪里不合理？ | 分析流程耗时，发现"审批卡在某个环节" |
| 管理盲区在哪？ | 交叉分析：某些数据没人看、某些流程没人管 |

## 六、用户交互设计

### 6.1 传统 ERP vs AI-ERP 对比

#### 📋 数据录入

| 传统 ERP | AI-ERP |
|---------|--------|
| 十几个字段，必填项标红 | 一个对话框："帮我录入销售单，客户是XX，产品是XX..." |
| 填错一个弹窗报错 | AI 自动补全："客户是XX吗？我帮你找到了" |
| 下拉菜单选半天 | "上次卖的是什么？我帮你预填了" |

**保留简单输入窗口**作为备选项 —— 给不习惯 AI 的人用。

#### 🔍 数据查询

| 传统 ERP | AI-ERP |
|---------|--------|
| 复杂筛选器、多条件组合 | "上个月销售前三的产品是什么？" |
| 要知道字段名称、表结构 | "库存不足的产品有哪些？" |
| 查不到就是查不到 | "你是指原材料库存还是成品库存？我帮你查了一下..." |

#### 📋 任务分配

| 传统 ERP | AI-ERP |
|---------|--------|
| 手动选人、填任务、点发送 | "通知仓库盘点库存" |
| 不看系统不知道有任务 | AI 主动推："张三，有 3 个待审批单据" |
| 完成了还得手动点 | "李四完成了质检，下一条记录是..." |

### 6.2 AI 要"可见"，不要"隐形"

- **展示 AI 思考过程**："我帮你自动分类了，因为..."
- **让 AI 主动推送**："检测到 3 笔重复订单，需要处理吗？"
- **AI 的建议要可撤销**：错了可以改回来，客户才敢用

## 七、技术实现思路

### 7.1 技术选型（轻量级方案）

```
前端：Vue 3 + Element Plus（成熟、文档多、易上手）
AI 接入：Claude API / GPT API
数据库：暂时不动，用 ORM 做适配
部署：Docker 一键部署（客户现场直接跑）
```

### 7.2 分阶段实现

#### 第一阶段（2-3 个月）：MVP
```
├── Web 前端（Vue 3）
├── 一个 AI Chat 入口
├── 连接现有 ERP 数据库
└── 内置 3-5 个分析 Skill：
    - 财务健康分析 Skill
    - 生产效能诊断 Skill
    - 人力饱和度分析 Skill
    - 库存优化建议 Skill
```

#### 第二阶段（6 个月）：多 Agent 协同
```
├── 多个专业 Agent（财务、生产、人力）
├── Agent 协同机制
└── 更深入的 Skill 体系
```

#### 第三阶段（1 年+）：生态化
```
├── Skill 市场（内部）
├── 行业模板复用
└── 生态能力接入
```

## 九、风险与建议

### 9.1 风险提示

#### 风险 1："放宽数据约束"要有个度
- 建议保留**核心实体约束**（如客户 ID、产品 ID）
- 放宽**描述性字段**（名称、备注、分类等）
- 用 AI 做"后处理"而不是"没处理"

#### 风险 2：AI 能力要先聚焦，不要铺太开
"先上马"意味着要**选 1-2 个最打动客户的场景**：
- 智能问答（"上个月销售额多少？"）
- 智能填单（"帮我录入一笔采购单，供应商是某某"）
- 异常检测（"这周采购成本异常上升 20%"）

### 9.2 补充建议

#### 建议 1：考虑"双模式"运行
```
传统模式：严格约束、完整流程（适合大客户）
轻量模式：放宽约束、AI 辅助（适合小客户）
```

#### 建议 2：数据库迁移要"无痛"
- 用 **ORM 抽象层**（如 Prisma、TypeORM）隔离数据库差异
- 先在**新功能**上用非结构化存储，旧功能不动
- 提供**迁移工具**，一键把旧数据转过去

#### 建议 3：发现问题时"说人话"
```
❌ 错误："库存周转率 2.3，低于行业平均值"
✅ 正确："库存积压严重，资金被占用约 50 万，建议减少 XX 产品采购"
```

#### 建议 4：要有"行动建议"，不只是"问题发现"
```
问题：生产线瓶颈在装配环节
建议：
1. 调配 2 名包装员支援装配（预计提升 15% 产能）
2. 考虑增加一台半自动设备（投资回报期约 6 个月）
3. 调整生产排程，减少装配环节等待时间
```

## 十、飞书多维表格与双端架构设计

### 10.1 飞书多维表格：前端数据库

#### 什么是前端数据库？

| 传统后端数据库 | 飞书多维表格（前端数据库） |
|--------------|---------------------------|
| 后端存储，用户看不到 | 用户直接操作 |
| 需要 API/前端访问 | 可视化编辑 |
| 多用户协作需要应用层 | 天然支持实时协作 |
| 数据展示需要开发 | 多视图（表格/看板/甘特图） |

#### 飞书多维表格的核心特性

| 特性 | 说明 |
|-----|------|
| **字段类型** | 文本、数字、日期、单选/多选、人员、附件、关联字段、查找字段、公式 |
| **多视图** | 表格视图、看板视图、日历视图、甘特图、画册视图 |
| **数据关联** | 关联其他表的记录，自动获取关联信息 |
| **公式计算** | 自动计算字段（如金额=数量×单价） |
| **实时协作** | 多人同时编辑，实时同步 |
| **API 可编程** | 完整的 API 支持 CRUD 操作 |

#### 对 AiERP 的启发

| 启发点 | 说明 |
|-------|------|
| **数据结构要"半约束"** | 有字段类型防止数据太乱，但可以随时增删字段 |
| **前端交互要"多视图"** | 不同角色看到不同的视图（老板看仪表盘，销售看看板） |
| **数据关联要"可视化"** | 添加订单时直接从客户表选择，自动填充地址、价格 |
| **自动化 + AI = 行动式 AI** | 飞书自动化是固定规则，AI 可以智能判断 |

```
│  老客户：Delphi 客户端（核心业务，继续维护）              │
│  新客户：Web 端 + 飞书端（双端配合使用）                  │
└─────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────┐
│                    双端职责划分                          │
├──────────────────┬──────────────────────────────────────┤
│    Web 端         │            飞书端                    │
├──────────────────┼──────────────────────────────────────┤
│ 规范性数据录入    │ AI Chat 交互入口                     │
│ 核心业务操作      │ 汇总类数据展示                       │
│ 复杂表单处理      │ 任务类数据管理                       │
│ 报表查询与导出    │ 7×24 监控预警                       │
│ 系统配置管理      │ 移动端便捷操作                       │
└──────────────────┴──────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────┐
│                    AI 层（QClaw/QwClaw）                 │
├─────────────────────────────────────────────────────────┤
│  AI Agent + Skills（数据分析、问题发现、建议生成）       │
└─────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────┐
│                    数据层                                │
├─────────────────────────────────────────────────────────┤
│  后端：SQL Server（核心业务数据）                        │
│  前端：飞书多维表格（汇总数据、任务数据）                 │
└─────────────────────────────────────────────────────────┘
```

#### Web 端职责

| 场景 | 使用 Web 端的原因 |
|-----|------------------|
| **订单录入** | 需要严格的字段约束、必填校验、数据格式化 |
| **库存管理** | 需要精确的数量控制、批次管理、仓库区分 |
| **财务记账** | 需要借贷平衡、科目校验、凭证规范性 |
| **基础数据维护** | 客户档案、产品档案、供应商档案需要规范化 |
| **复杂报表查询** | 多条件组合查询、数据导出、打印 |
| **系统配置** | 权限配置、流程配置、参数设置 |

#### 飞书端职责

| 场景 | 使用飞书端的原因 |
|-----|------------------|
| **AI Chat 查询** | "上个月销售情况怎么样？" —— 自然语言更便捷 |
| **汇总数据查看** | 老板看仪表盘、关键指标 —— 可视化展示 |
| **任务管理** | "张三今天要干什么" —— 任务看板、日历视图 |
| **进度跟踪** | 生产进度、订单进度 —— 多视图展示 |
| **考核分析** | 人员绩效、部门效率 —— 图表化呈现 |
| **移动端操作** | 外出时快速查询、审批 —— 手机方便 |
| **7×24 预警** | 异常自动推送 —— 实时通知 |

### 10.3 为什么不用飞书多维表格管理全部数据？

#### 技术限制

| 限制 | 飞书多维表格 | SQL Server |
|-----|-------------|------------|
| 单表数据量限制 | 有限制 | 几乎无限制（百万/千万级） |
| 表数量限制 | 有限制 | 无限制 |
| 查询性能 | 简单查询快，复杂查询慢 | 优化后很快 |
| 事务支持 | 弱（不支持 ACID） | 强（完整的事务支持） |
| 数据完整性约束 | 弱（只有基础验证） | 强（外键、触发器、存储过程） |
| 并发控制 | 弱 | 强（锁机制、MVCC） |

#### 实际问题

```
假设全部用飞书多维表格：

50+ 张表 × 平均 1 万条数据 = 50 万条数据
    ↓
问题：
├── 飞书空间会变得非常混乱
├── 查询性能急剧下降
├── 数据关系难以维护（外键、级联）
├── 业务逻辑无法保证（库存扣减、财务记账）
├── 并发冲突严重（多人同时操作）
└── 数据安全风险（误删、误改难以恢复）
```

### 10.4 数据分层设计

#### 后端数据库：40-50 张表（核心业务）

| 表类型 | 表数量 | 数据量级 | 原因 |
|-------|--------|---------|------|
| 基础数据 | 10-20 张 | 5 万+ 条 | 需要严格约束、频繁查询 |
| 业务数据 | 20-30 张 | 50 万+ 条 | 核心交易、高并发、强一致性 |
| 系统数据 | 5-10 张 | 100 万+ 条 | 日志、审计、配置 |

#### 前端数据库：10-20 张表（汇总 + 协作）

| 表类型 | 表数量 | 数据量级 | 原因 |
|-------|--------|---------|------|
| 汇总数据 | 5-10 张 | 几千条 | 聚合后的数据，数据量小 |
| 任务数据 | 3-5 张 | 几百条 | 协作数据，日常使用 |
| 分析结果 | 3-5 张 | 几十条 | AI 生成，数量有限 |

#### 数据分类决策树

```
数据需要存到哪里？
    ↓
是核心业务数据吗？（订单、库存、财务、生产等）
    │ 是                        │ 否
    ↓                           ↓
后端数据库              是汇总/统计数据吗？
                        │ 是          │ 否
                        ↓             ↓
                    前端数据库    是任务/协作数据？
                                    │ 是      │ 否
                                    ↓         ↓
                                前端数据库  后端数据库
```

## 十一、OpenClaw/QClaw：AI Agent 方案

### 11.1 OpenClaw 的核心能力

| 能力 | 说明 |
|-----|------|
| **执行能力** | 给 AI 配一台电脑，通过聊天接收指令并完成任务 |
| **拥有记忆** | 能记住你的偏好，真正做到懂你、专属于你 |
| **持续进化** | 开源技能社区，让 AI 可以快速掌握各类技能 |
| **主动 7×24 小时干活** | 24 小时无休干活，定时执行，主动汇报、自主组建团队 |

### 11.2 飞书 + OpenClaw 架构

```
原有 Delphi ERP（不动，继续维护老客户）
    ↓
数据同步 / 视图层
    ↓
飞书多维表格（作为新前端 + 数据展示）
    ↓
飞书机器人 + AI Chat（交互入口 + 执行引擎）
    ↓
用户在飞书里完成所有操作
```

### 11.3 安全性考虑：使用国内大厂方案

| 方案 | 优势 | 适用场景 |
|-----|------|---------|
| **QClaw** | 国内大厂背书、安全保障 | 通用场景 |
| **QwClaw** | 企业级安全、合规性强 | 对安全要求高的客户 |
| **OpenClaw** | 开源、灵活 | 技术团队强、可自维护 |

**推荐**：使用 QClaw/QwClaw 等国内大厂方案，安全性和合规性更有保障。

## 十二、SQL Server 与飞书数据同步方案

### 12.1 技术可行性评估

| 难度点 | 评估 |
|-------|------|
| **开发复杂度** | ⭐⭐☆☆☆（中等） |
| **维护成本** | ⭐⭐☆☆☆（中等） |
| **技术风险** | ⭐☆☆☆☆（低） |
| **数据一致性** | ⭐⭐⭐☆☆（中等） |

**总体评估**：技术上**完全可行**，难度不大。

### 12.2 数据同步的三种方案

#### 方案 1：单向同步（SQL Server → 飞书）

```
SQL Server（主数据）
    ↓
定时任务（如每小时）
    ↓
飞书多维表格（只读副本）
```

**适用场景**：基础数据、汇总数据
**实现难度**：⭐☆☆☆☆（简单）

#### 方案 2：双向同步（SQL Server ↔ 飞书）

```
SQL Server ←→ 同步服务 ←→ 飞书多维表格
```

**适用场景**：任务数据、协作数据
**实现难度**：⭐⭐⭐☆☆（中等）

#### 方案 3：混合方案（推荐）

```
SQL Server（主数据）
    ↓ 单向同步
飞书多维表格（只读副本）
    ↓
AI/用户操作
    ↓
通过 API 写回 SQL Server（而不是直接改飞书）
```

**适用场景**：大部分场景
**实现难度**：⭐⭐☆☆☆（简单-中等）

### 12.3 技术实现建议

#### 技术栈

```
编程语言：
├── Node.js（推荐）
│   ├── 飞书 SDK（@larksuiteoapi/node-sdk）
│   ├── SQL Server 驱动（mssql / tedious）
│   └── 生态丰富，易于开发
│
└── Python（备选）
    ├── 飞书 SDK（lark-oapi）
    ├── pymssql / pyodbc
    └── 适合数据处理

部署：
├── 云服务器（阿里云、腾讯云）
├── Docker 容器化
└── 定时任务（node-cron / APScheduler）
```

#### 同步策略

| 数据类型 | 同步方式 | 频率 | 原因 |
|---------|---------|------|------|
| **基础数据**<br/>（客户、产品、供应商） | 定时同步 | 每小时 | 变更不频繁，延迟可接受 |
| **业务数据**<br/>（订单、库存） | 实时同步 | 立即 | 需要及时反馈 |
| **汇总数据**<br/>（销售日报、库存汇总） | 定时聚合 | 每天 | 统计分析用，不需要实时 |
| **任务数据**<br/>（待办、分配） | 双向同步 | 实时 | 协作需要，两边都可能改 |
| **分析结果**<br/>（AI 报告） | 单向写入 | 按需 | AI 生成后直接写飞书 |
